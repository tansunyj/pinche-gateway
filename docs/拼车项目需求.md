## 1. 项目背景与目标

**一句话**：做一个面向**开发者 / 小B** 的 AI 额度零售平台，核心玩法是「**拼车**」——平台在管理后台接入各种 AI 渠道商/官方 AI，**为各个模型发起拼车车次**（折扣券），用户通过**分享链接免费上车**，激活该车次的模型折扣；车次满员或过期后不再显示；平台持续发起新车次，用户可加入多个车次，实际生效折扣取**未过期车次中折扣率最低**者。

**三层关系**：

```
[ 上游 AI 渠道商 / 官方 AI ]            ← pinche/gateway 的 proxy_channels（零改动复用）
        ↑ 网关能力
[ pinche/gateway 网关 ]                 ← 路由 / 计费 / 折扣 / 结算 / API Key 认证（已有，跑在生产）
        ↑ 业务对接（开户 / 发 Key / 充值到账 / 写折扣）
[ 拼车程序（本项目，全新）]              ← 注册 / 充值 / 车次 / 折扣 / 用量展示（前后端一体）
        ↑ 开发者 / 小B
[ 下游应用（SDK 调用）]                  ← 拿 API Key，OpenAI/Anthropic/Responses 协议接入
```

### 1.1 部署形态（已确认）：两个独立程序

```
┌────────────────────────────────┐        ┌────────────────────────────────┐
│  pinche/gateway 网关（独立）     │        │  拼车程序（独立，前后端一体）     │

│  · /v1/* 开发者协议入口（API Key）│        │  后端：注册/充值/车次/折扣/支付   │
│  ·                             │◄──────►│  · 拼车后端直连网关 MySQL 读写   │
└────────────────────────────────┘ 直连DB  │  · 改动余额后清网关 Redis 缓存键  │
      ▲              ▲                └────────────────────────────────┘
      │ SDK(OpenAI/Anthropic)│ 浏览器用户（普通用户 / 管理员）
      └── 下游应用 ──────────┴─────────
```

- **网关**：只管「模型转发 + 计费 + 折扣 + Key 认证」，**零 Java 改造**；无 `/admin/*` 管理接口
- **拼车程序**：一切业务（用户/充值/车次/折扣/支付/消费日志查看）；**直连网关 MySQL** 读写 `user_users` / `proxy_tokens` / `user_model_discounts` / `proxy_logs` 等表
- **唯一耦合**：改余额后必须清网关 Redis 键 `user_balance:{userId}`（见 §6.3），拼车程序需能连网关 Redis

## 2. 核心业务模型：拼车（平台发车）

### 2.1 两个解耦的配置

- **充值档位**：只定义「金额 → 零售额度」（如 ¥100 = 100 万额度），**不含折扣**。用户充多少得多少，与拼车无关
- **车次**：定义「多个模型分组 + 各组折扣率 + 名额 + 有效期」，**不含金额**。车次 = 一组模型的**折扣券包**，满员/过期即失效
- 用户先充值拿通用额度，再上车拿模型折扣（一次上车获得该车次所有模型的折扣），消费时网关按折扣扣额度

### 2.2 核心流程

```
发车（平台）: 管理后台接入渠道 → 发起车次 {名称, 模型分组[{分组名, 折扣率, 模型列表}], 名额 N, 有效期}
             → 生成分享链接 → 前端车次列表展示（仅 ACTIVE 且未满员且未过期）
充值（用户）: 充值档位列表 → 选金额 → 支付宝支付 → 到账零售额度（首次充值自动开户 + 发默认 Key）
上车（用户）: 点车次分享链接 → 登录/注册 → 免费上车 → 激活该车次所有模型折扣（遍历写网关 user_model_discounts）
消费（用户）: API Key 调用模型 → 网关按【该模型最优折扣】计费扣额度
满员/过期: 名额满 → 前端不再显示、不可上车；到期 → 定时撤销该车次所有模型折扣（node-cron）
新车次: 平台继续发新车次 → 用户可加入，享受对应折扣
```

### 2.3 规则参数（平台方可配置）

**车次参数**：

| 参数 | 说明 |
|------|------|
| 车次名称 | 如「DeepSeek 全家桶特惠」「全模型限时折扣」 |
| 模型分组 | **一车次多分组，每分组多模型，各组独立折扣**（见下方结构） |
| 名额 | 目标上车人数 N（满员即不再显示/不可上车） |
| 有效期 | 车次有效时长，到期折扣撤销 |
| 班次类型 | `SHORT_TERM` 短期 / `LONG_TERM` 长期 / `PERMANENT` 永久（见下方详细说明） |
| 上车截止时间 | 截止后不可上车（永久车次必填，短期/长期默认=折扣过期时间） |
| 可见性 | `PUBLIC` 公开（有分享链接）/ `USER_LIST` 指定用户（无分享链接） |
| 状态 | `ACTIVE` 进行中 / `FULL` 已满员 / `EXPIRED` 已过期 / `CLOSED` 人工关闭 |

**车次类型详细说明（v0.8 新增）**：

| 类型 | 折扣有效期 | 上车截止 | 满员后展示 | 典型场景 |
|------|-----------|---------|-----------|---------|
| `SHORT_TERM` 短期 | 如 7 天，到期撤销 | 到期即截止 | 「更多车次」展示 **7 天** | 限时特惠 |
| `LONG_TERM` 长期 | 如 30 天/季度，可续期 | 到期即截止 | 「更多车次」展示 **30 天** | 月度/季度折扣 |
| `PERMANENT` 永久 | **永久有效，不撤销** | 需单独设置 | 「更多车次」**一直展示** | 长期合作、VIP专属 |

**活跃度回收机制（v0.8 新增，防占坑）**：

针对 `LONG_TERM` 和 `PERMANENT` 车次，防止羊毛党占坑不消费：

| 规则 | 说明 |
|------|------|
| 触发条件 | 上车后连续 **15 天** 对该车次包含的模型 **无任何消费记录** |
| 处理动作 | 自动"请出车次"：释放名额（`current_count - 1`）+ 撤销对应折扣 |
| 执行时机 | node-cron 每日凌晨扫描 |
| 豁免条件 | 用户在该车次的累计消费 ≥ 1 万额度（已证明是活跃用户） |
| 通知 | 被请出前 3 天发站内消息提醒："您在 XX 车次即将因不活跃被移出，请尽快使用" |

```sql
-- 查找需要回收的用户
SELECT rm.user_id, rm.ride_id
FROM pt_ride_members rm
JOIN pt_rides r ON rm.ride_id = r.id
WHERE r.ride_type IN ('LONG_TERM', 'PERMANENT')
  AND r.status = 'ACTIVE'
  AND rm.joined_at < DATE_SUB(NOW(), INTERVAL 15 DAY)
  AND NOT EXISTS (
    -- 最近15天有消费记录
    SELECT 1 FROM proxy_logs pl
    JOIN pt_ride_group_models rgm ON pl.model_id = rgm.model_id
    JOIN pt_ride_groups rg ON rgm.group_id = rg.id
    WHERE pl.user_id = rm.user_id
      AND rg.ride_id = rm.ride_id
      AND pl.created_at > DATE_SUB(NOW(), INTERVAL 15 DAY)
  )
  AND rm.total_consumption < 10000; -- 累计消费不足1万额度
```

| `PUBLIC` 公开 | 所有用户 | ✅ 有，可分享传播 | 常规营销车次 |

**分组规则**：
| 规则 | 说明 |
|------|------|
| 分组数量 | 一个车次至少 1 个分组，无上限 |
| 分组内模型 | 每个分组至少 1 个模型，无上限 |
| 模型唯一性 | **同一车次内，一个模型只能出现在一个分组中**（不可重复） |
| 上车方式 | 用户上车 = **一次性获得该车次所有分组的所有模型折扣** |

**模型去重校验（v0.8 新增）**：
- 数据库层：`pt_ride_group_models` 表有联合唯一索引 `uk_ride_model (ride_id, model_id)`
- **API 校验层（必须）**：发起/编辑车次时，后端 Validator 必须在保存前做全局去重：
  ```typescript
  // 将所有分组的模型扁平化，检查是否有重复
  const allModels = groups.flatMap(g => g.modelIds);
  const uniqueModels = new Set(allModels);
  if (allModels.length !== uniqueModels.size) {
    throw new BadRequestError('车次内不能在不同分组重复添加相同模型');
  }
  ```
- 目的：在 API 层友好拦截，避免数据库唯一索引报错返回不友好的 500

### 2.4 关键业务规则

**多车次择优（核心）**
- 用户可同时加入多个车次（不同车次可能包含相同模型）
- 实际生效折扣 = 用户已加入的**未过期**车次中，该模型的**折扣率最低**（最优）者
- 例：A 车含 deepseek-chat 6折 + B 车含 deepseek-chat 8折 → **6折生效**；A 车过期后 → 8折生效；全部过期 → 无折扣
- 网关侧 `user_model_discounts` 同 (userId, modelId) 多配置取 min，**天然支持**；拼车程序保证不写过期车次折扣 + 定期撤销过期车次折扣行

**折扣生命周期**（v0.8.2 最终版，已确认）

> ✅ 网关**已确认**会过滤 `end_time < NOW()` 的行，**不需要过期撤销任务**！

- **上车即写**：免费上车成功 → 遍历车次所有分组的所有模型，**每个模型 INSERT 一行**到 `user_model_discounts`：
  ```sql
  INSERT INTO user_model_discounts 
    (user_id, models, discount_type, discount_value, end_time, status, remark)
  VALUES 
    (:userId, '["aliyun/deepseek-v4-flash"]', 'PERCENTAGE', 0.6, '2026-09-01 00:00:00', 1, 'ride:1001');
  -- 注意：models 字段是 JSON 数组格式，模型 ID 带渠道前缀
  ```
- **满员车次**：只是关闭上车、按时间显示；已上车用户继续享受折扣至 `end_time`
- **过期车次**：**无需任何操作！** 网关查询时自动过滤 `end_time < NOW()` 的行
- **手动撤销**：管理员关闭车次时 `UPDATE status=0 WHERE remark='ride:xxx'`
- **多车次择优**：网关自动在多行中取 `discount_value` 的 min，**拼车程序不需要计算**
- **短期/长期/永久班次**：通过 `end_time` 区分（永久车次 `end_time=NULL`）

**最终方案优势**：
- ✅ **不需要过期撤销任务**（网关自动过滤）
- ✅ **不需要分布式锁**（没有并发重算问题）
- ✅ **不需要计算最优折扣**（网关自动取 min）
- ✅ **不需要 Key 哈希算法**（明文存储）
- ✅ 逻辑大幅简化，开发周期缩短

**上车关闭规则（硬性，二选一即关，关闭后不再开放）**
- **满员发车关闭**：`current_count ≥ target_count`（状态置 `FULL`）→ 不允许加入，前端不再显示
- **到期关闭**：`expire_at` 已到（状态置 `EXPIRED`，**无论是否满员**）→ 不允许加入，前端不再显示
- 两种关闭互不依赖：先满员 → 满员即关；先到期（哪怕没满员）→ 到期即关；满员后到期 → 仍保持关闭
- 已上车成员不受关闭影响：满员车次的成员继续享折扣至车次过期；到期车次的折扣按上述撤销逻辑处理

**充值**
- 用户**直接充值**（零售价，首期开放——推翻 v0.5「首期不做」）：支付宝 → 到账零售额度
- **注册即开户**（v0.8 调整）：注册成功时即在网关开户（余额=0）+ 发默认 Key，用户可提前配置 Key 到客户端，充值后无缝使用

### 2.5 异常与边界（首期处理策略）

| 场景 | 处理 |
|------|------|
| 充值支付回调丢失 | 定时查单/对账补单（照 website_backend 支付宝模式） |
| 充值重复到账 | 业务单号幂等 + `out_trade_no` 唯一 + Redis 到账锁 |
| 充值到账跨库事务失败 | 回调仅记录流水，由异步 Worker 推进"加余额+清缓存"，失败自动重试（见 §2.6） |
| 车次并发抢名额 | 条件 `UPDATE`（受影响行数判定）防超卖；可加 Redis 锁兜底 |
| 同一用户重复上车同车次 | `pt_ride_members (ride_id, user_id)` 唯一约束，幂等 |
| 折扣写入失败 | 记录待重试队列；车次侧不影响上车（`user_model_discounts` 直写 DB） |
| 过期撤销与用户正在消费并发 | 先查再写，业务单号幂等；网关 min 兜底 |
| 用户注册但从未充值 | 已有网关账户（余额=0）+ 已有 Key；调用时余额不足返回 `402 Insufficient Balance` |

### 2.6 充值到账可靠性机制（v0.8 新增）

**问题**：充值回调需要跨库操作（拼车库 `pt_payments` → 网关库 `user_users.balance` → 网关 Redis 缓存），中途失败会导致"钱付了但额度没到账"。

**解决方案：异步任务队列 + 本地补偿**

```
支付宝回调 → 仅验签 + 记录流水（status=CALLBACK_RECEIVED）
         ↓
    异步 Worker 消费任务
         ↓
    1. 更新网关 user_users.balance
    2. 删除网关 Redis 缓存键
    3. 更新 pt_payments.status = SUCCESS
         ↓
    失败则指数退避重试（1s → 2s → 4s → 8s → ...）
    超过 5 次失败 → 告警人工介入
```

**流水状态机**：
```
PENDING → CALLBACK_RECEIVED → SUCCESS
                ↓
            PROCESSING（Worker处理中）
                ↓
            FAILED（重试耗尽，需人工）
```

**实现要点**：
- 使用 BullMQ 或本地重试表（`pt_payment_tasks`）实现可靠任务队列
- 支付宝回调接口必须快速返回 `success`（5秒内），避免支付宝重复回调
- Worker 处理时加 Redis 锁（`pt:lock:payment:{orderId}`），防止重复处理

## 4. 功能清单（按模块）

### 4.1 用户与账户（前端 + 后端）
- 注册 / 登录（**已定：手机号 + 短信验证码**；不做微信登录）
- 个人信息、修改密码
- **开户时机（v0.8 调整）**：**注册时即在网关开户 + 发默认 Key**（余额为 0），用户可提前获取 Key 配置到客户端，充值后无缝使用；调用时余额不足返回 `402 Insufficient Balance`

## 5. 数据模型草案（初稿，待细化）

### 5.1 存储选型（已定：拼车程序 **Redis + MySQL**）

- 拼车程序用 **MySQL（独立库，如 `pt_carpool`）+ Redis**（推翻 v0.6「纯 MySQL」；v0.7 起拼车程序本来就要连网关 Redis 清余额缓存键，自己用 Redis 做业务状态/锁/幂等顺理成章）
- **MySQL 承担真相与强一致**（照 v0.6 评估，全部可行，作为兜底/账本）：
  - **名额防超卖**：`UPDATE pt_rides SET current_count = current_count + 1 WHERE id=? AND status='ACTIVE' AND current_count < target_count`（受影响行数判定，原子）
  - **上车幂等**：`pt_ride_members (ride_id, user_id)` 唯一约束
  - **满员置 FULL**：条件 `UPDATE pt_rides SET status='FULL' WHERE id=? AND status='ACTIVE' AND current_count = target_count`（affected=1 才触发，防双写）
  - **充值到账幂等**：`out_trade_no` 唯一 + 业务单号幂等表
  - **过期撤销**：node-cron 扫描 + 条件 UPDATE + 重算最优折扣覆写
  - **充值回调补单**：node-cron 定时查单对账
- **Redis 承担热状态与并发护栏**：
  - **余额缓存键管理**：直写网关 `user_users.balance` 后 DELETE 网关 Redis 键 `user_balance:{userId}`（§6.3，**必须**）
  - **车次状态热缓存**：车次列表/进度/满员标记可缓存，DB 仍是真相
  - **到账/上车/写折扣的分布式锁**（防多实例双写）
  - **幂等键 + 限流**：支付回调补单、上车、写折扣的原子去重
  - Web 登录态：JWT（无状态），Redis 仅作会话黑名单/可选
- 二期多实例水平扩展时，Redis 已是现成的，无需再引入

### 5.2 表结构草案

```
pt_users              拼车平台用户（phone, password_hash, auth_type）
  ├── user_users_id   → 映射网关 user_users.id（首次充值开户后回填，注册未充值为 NULL）

pt_recharge_tiers     充值档位（amount_yuan, quota, enabled）

pt_rides              车次（name, target_count, current_count, expire_at,
                        ride_type[SHORT_TERM/LONG_TERM], status[ACTIVE/FULL/EXPIRED/CLOSED],
                        share_token, created_at）
                        ↓ 1:N
pt_ride_groups        模型分组（ride_id, group_name, discount_rate）
                        ↓ 1:N
pt_ride_group_models  分组模型（group_id, model_id, UNIQUE(ride_id, model_id) 保证同车次模型不重复）

pt_ride_members       上车记录（ride_id, user_id, joined_at, UNIQUE(ride_id, user_id)）

pt_payments           充值支付流水（order_no, user_id, tier_id, amount_yuan, quota, provider[alipay],
                        status[PENDING/SUCCESS/FAILED/REFUNDED], out_trade_no, refund_no, UNIQUE(out_trade_no)）
```

### 5.3 关键事务

**充值到账**（支付宝回调）：
1. 写 `pt_payments` = SUCCESS（`out_trade_no` 唯一，幂等；Redis 到账锁防重）
2. 若用户未开户 → **直写网关 `user_users` 开户** → 回填 `user_users_id` → **直写 `proxy_tokens` 发默认 Key**
3. **直写网关 `user_users.balance = balance + :amount`**（原子相对更新）→ **DELETE 网关 Redis 键 `user_balance:{userId}`**（业务单号 = payment order_no 幂等）

**上车激活折扣**：
1. 插入 `pt_ride_members`（唯一约束幂等）
2. 条件 `UPDATE pt_rides SET current_count = current_count + 1 WHERE ... AND current_count < target_count`（失败=已满员，返回"名额已满"）
3. **遍历车次所有分组 → 所有模型 → 逐一直写网关 `user_model_discounts`**（userId + modelId + rate，业务单号 = 车次单号 + modelId 幂等）
4. current_count 达到 target → 条件 UPDATE 置 FULL → 前端隐藏

**过期撤销折扣**（node-cron）：
1. 扫描 `EXPIRED` 车次
2. 对每个成员 + 该车次涉及的每个模型：查该用户该模型**其余未过期车次** → 有则**直写 `user_model_discounts` 覆写最优折扣**；无则撤销该折扣行

## 6. 与 pinche/gateway 网关的对接设计（定稿：拼车程序直连 MySQL + Redis）

> 已拍板：**网关不再新增任何 `/admin/*` 接口**（推翻 v0.6「网关新增 HTTP 管理 API」）。拼车程序**直连网关 MySQL** 完成开户/发 Key/充值/写折扣/查消费日志；**改动余额后必须清网关 Redis 缓存键**（§6.3）。网关 Java 程序 **零改造**。

网关侧事实（已核实，2026-08-19）：
- 网关**无 `/admin/*` 接口**；现有 admin_backend 是直连 MySQL 管理配置表——拼车程序照此模式
- 用户表 `user_users`（`balance` 额度 Long）、Key 表 `proxy_tokens`、折扣表 `user_model_discounts`
- **API Key 认证无缓存**：`ApiKeyAuthWebFilter` → `ApiKeyAuthService` 直读 `proxy_tokens`（源码无 Redis 引用）→ 拼车程序直接 INSERT 即生效
- **折扣查询无缓存**：`UserModelDiscountsService` 每次请求实时 `findActiveDiscountsByUserId` 查 DB → 直写 `user_model_discounts` 即生效
- **余额有 Redis 缓存**：`UserBalanceService` 用键 `user_balance:{userId}` + DB 兜底 → **改完余额必须 DELETE 该键**（唯一耦合点）
- 计费口径：1 元 = 100000 额度

### 6.1 拼车程序直连网关 MySQL 的操作清单（替代原管理 API）

> 全部由拼车程序后端在事务内完成；表结构照网关现有 DDL。

| 操作 | 直连实现 |
|------|------|
| 开户 | INSERT `user_users`（balance=0）→ 回填 `pt_users.user_users_id` |
| 发 API Key | INSERT `proxy_tokens`（明文 key 只返回一次；加密态存库，照现有字段） |
| 充值到账 | 原子相对更新 `user_users.balance = balance + :amount` → **DELETE Redis `user_balance:{userId}`** |
| 余额调整（退款/补偿） | 同上（正/负），业务单号幂等 |
| 写 / 撤销模型折扣 | INSERT / UPDATE / DELETE `user_model_discounts`（rate、models JSON，业务单号幂等） |
| 查余额 | 读 `user_users.balance`（展示层换算元） |
| 查消费日志（展示） | 直连**只读** `proxy_logs` / `proxy_request_logs` |

❓待确认：
- 折扣撤销用「UPDATE rate 更高（1.0）」还是「DELETE 行」——网关 min 语义下 DELETE 更干净，但需保证撤销幂等
- 是否给拼车用户开放多 Key 创建上限（首期：默认 Key 即可，禁用走 DELETE 直连）

### 6.2 管理面鉴权（已定：各是各的）

- **网关侧**：`/v1/*` 保持现有 `ApiKeyAuthWebFilter` **API Key 鉴权**（消费/查余额照常）；**无 `/admin/*`，不需要管理 Key**
- **拼车程序侧**：自己的 Web 登录用**登录态**（JWT），与网关 Key 完全隔离——拼车用户登录 ≠ 能调网关任何接口，网关只认它自己的 Key
- 拼车程序访问网关 MySQL/Redis 用**数据库凭据**（独立账号，生产凭证须保私有），不走网关 HTTP

### 6.3 一致性（唯一耦合点：余额 Redis 缓存键）

- **余额写入后必须清缓存**：拼车程序直写 `user_users.balance` 后，**DELETE 网关 Redis 键 `user_balance:{userId}`**（`CacheConstants.userBalanceKey(userId)`）；网关下一次读取走 DB 兜底自动重建缓存——不清则网关读到旧余额
- **充值原子性**：`UPDATE user_users SET balance = balance + :amount`（原子相对更新，禁读改写）+ DELETE 缓存键同一脚本完成；业务单号幂等 + Redis 到账锁防重复
- **Key 与折扣无缓存**：直写 `proxy_tokens` / `user_model_discounts` 即生效，无需清任何缓存
- 网关自身计费/折扣链路不变（min 兜底照旧）

### 6.4 拼车折扣进入网关计费（已确认，零网关改动）

拼车折扣必须**进入网关计费**——下游按 API Key 实时消费，额度扣减发生在网关，折扣要在消费那一刻生效（对应 §1.2 能力边界）。

**载体：复用现有 `user_model_discounts` 机制**
- `UserModelDiscountsService.getDiscountRate(userId, modelId)`：返回折扣倍率（0.8 = 8 折），同 (userId, modelId) 多配置取 min；已与 API Key markup、套餐三者取 min
- **上车即写**：免费上车成功 → 直写 `user_model_discounts`（业务单号幂等）→ 后续消费网关自动打折，**无需新增计费代码**
- **过期撤销**：node-cron 撤销过期车次折扣时，重算该用户该模型剩余未过期车次的最优折扣并覆写（min 语义）

**折扣粒度（已定：按模型）**
- 一个车次包含多个分组，每个分组有独立折扣率和多个模型
- 上车时遍历所有分组的所有模型，逐一按 (userId, modelId, rate) 写入网关
- 同一模型在多个未过期车次中 → 网关 min 自动取最优

**多车次择优（用户规则 = 网关 min 行为）**
- 用户可同时在多个车次里；生效折扣 = 未过期车次中折扣率最低者
- 网关按行取 min，天然满足；拼车程序只需保证不写过期车次折扣、过期及时撤销/覆写

**充值侧 vs 消费侧（已定：消费侧）**
- **消费侧折扣**：充值按零售价到账（金额→额度，无折扣），消费时网关按折扣扣额度（成员感知=额度更耐用）✓
- ~~充值侧折扣~~：充值打折、按原额到账（已排除）

### 6.5 边界（首期明确不做，二期可加）

- ❌ 用量/消费明细聚合接口（拼车程序首期**直连只读** `proxy_logs` / `proxy_request_logs` 展示）、❌ 模型+价格列表接口（直连读 `model_library` / `model_prices`）
- ❌ 网关侧不新增任何接口（含 admin 管理 API）

## 8.1 架构风险与缓解措施（v0.8 新增）

### 风险 1：直连网关 DB 的数据一致性

**场景**：拼车程序直写 `user_users.balance`，如果应用崩溃在"写 DB"和"清 Redis 缓存"之间，网关会读到旧余额。

**⚠️ 缓存更新顺序必须是「先写库 → 成功后删缓存」**（v0.8.1 修正）：

> **错误做法**：「先删缓存 → 再写库」
> - 删除缓存和写 DB 之间如果有并发的余额查询请求打进来，网关会读到 DB 旧值并把它**重新写回缓存**
> - 之后即便 DB 更新成功了，缓存也会一直是旧值，直到 TTL 过期（可能达 60 秒）
> - 金额相关的缓存更新，**绝对不能**先删后写

**正确做法**：
```javascript
// 方案：先写库，成功后删缓存（Cache-Aside 标准模式）
async function rechargeBalance(userId, amount, orderNo) {
  // 1. 先写 DB（幂等，业务单号去重）
  const result = await db.execute(
    `UPDATE user_users SET balance = balance + ? WHERE id = ?`,
    [amount, userId]
  );
  
  if (result.affectedRows === 0) {
    throw new Error('余额更新失败');
  }
  
  // 2. 写库成功后，删除缓存（网关下次查询会从 DB 重建缓存）
  await redis.del(`user_balance:${userId}`);
  
  // 3. 如果删缓存失败，记录日志并重试，但不回滚 DB
  // 最坏情况：缓存 TTL 过期后自动更新（60秒内）
}
```

**一致性保障**：
- 写库成功 + 删缓存成功 → 立即一致
- 写库成功 + 删缓存失败 → 最终一致（等 TTL 过期，最多 60 秒）
- 写库失败 → 不删缓存，数据一致

### 风险 2：node-cron 过期撤销的可靠性

**场景**：单实例 node-cron 崩溃 → 过期车次折扣未撤销 → 用户继续享用过期折扣。

**缓解措施**：
```javascript
// 方案：每分钟扫描 + last_checked_at 防漏
async function expireRidesJob() {
  const expiredRides = await db.query(`
    SELECT id FROM pt_rides 
    WHERE status = 'ACTIVE' 
      AND expire_at < NOW() 
      AND (last_checked_at IS NULL OR last_checked_at < DATE_SUB(NOW(), INTERVAL 1 MINUTE))
    LIMIT 100
  `);
  
  for (const ride of expiredRides) {
    await processExpiredRide(ride.id);
    await db.execute(`UPDATE pt_rides SET last_checked_at = NOW() WHERE id = ?`, [ride.id]);
  }
}

// 每分钟执行，而非一次性定时
cron.schedule('* * * * *', expireRidesJob);
```

**二期升级**：用 Bull Queue + Redis 持久化任务队列，支持重试和死信。

### 风险 3：并发上车抢名额

**场景**：高并发下条件 UPDATE 仍可能超卖（虽然概率低）。

**缓解措施**：
```javascript
// 方案：MySQL 条件 UPDATE + Redis 分布式锁（双保险）
async function joinRide(rideId, userId) {
  const lockKey = `ride:${rideId}:join_lock`;
  const lock = await redis.set(lockKey, '1', 'NX', 'EX', 5); // 5 秒锁
  
  if (!lock) {
    throw new Error('系统繁忙，请稍后重试');
  }
  
  try {
    // MySQL 条件 UPDATE（原子，防超卖）
    const result = await db.execute(`
      UPDATE pt_rides 
      SET current_count = current_count + 1 
      WHERE id = ? AND status = 'ACTIVE' AND current_count < target_count
    `, [rideId]);
    
    if (result.affectedRows === 0) {
      throw new Error('名额已满');
    }
    
    // 插入成员记录（唯一约束幂等）
    await db.execute(`INSERT IGNORE INTO pt_ride_members (ride_id, user_id) VALUES (?, ?)`, [rideId, userId]);
    
  } finally {
    await redis.del(lockKey);
  }
}
```

### 风险 4：支付回调丢失或重复

**缓解措施**：
- **丢失**：每日凌晨对账 + 每 5 分钟查询 PENDING 订单主动查单
- **重复**：`out_trade_no` 唯一约束 + Redis 到账锁（`pay:callback:{outTradeNo}`，TTL 5 分钟）

### 对接（直连）相关

#### 问题 1：折扣撤销用 UPDATE 还是 DELETE？

| 方案 | 优点 | 缺点 |
|------|------|------|
| UPDATE rate=1.0 | 保留历史记录、可追溯 | 表行数膨胀、网关 min 仍要过滤 |
| DELETE 行 | 干净、网关无废数据 | 历史不可追溯 |

**✅ 建议决策**：**DELETE 行 + 归档表**
- 撤销时先 INSERT 到 `user_model_discounts_history`（归档），再 DELETE 原行
- 网关读折扣更干净，无需过滤 rate=1.0 的行
- 历史可追溯（归档表保留：userId, modelId, rate, rideId, expired_at）

#### 问题 2：网关 MySQL/Redis 账号权限划分

**✅ 建议决策**：
```sql
-- 拼车写账号（开户/发Key/充值/写折扣）
CREATE USER 'pt_writer'@'%' IDENTIFIED BY '***';
GRANT SELECT, INSERT, UPDATE, DELETE ON silievo_prod.user_users TO 'pt_writer'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON silievo_prod.proxy_tokens TO 'pt_writer'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON silievo_prod.user_model_discounts TO 'pt_writer'@'%';

-- 拼车读账号（消费日志/模型列表）
CREATE USER 'pt_reader'@'%' IDENTIFIED BY '***';
GRANT SELECT ON silievo_prod.proxy_logs TO 'pt_reader'@'%';
GRANT SELECT ON silievo_prod.proxy_request_logs TO 'pt_reader'@'%';
GRANT SELECT ON silievo_prod.model_library TO 'pt_reader'@'%';

```

Redis 权限：拼车程序只需 `DEL` 权限于 `user_balance:*` 键（通过 Lua 脚本限制 key pattern）

### 拼车业务相关

#### 问题 3：车次过期后折扣立即撤销还是宽限？

**✅ 建议决策**：**立即撤销，无宽限**
- 理由：折扣是"车次"的附属，车次过期 = 折扣失效，逻辑清晰
- 用户体验补偿：过期前 3 天 / 24 小时 / 1 小时多次提醒（二期实现）

#### 问题 4：长期班次续期机制

**✅ 建议决策**：**二期再定，首期不做**
- 可选方案 A：自动续费（需用户授权支付）
- 可选方案 B：到期前 N 天提醒，手动续期
- 首期长期班次到期直接撤销，用户需上新车次

#### 问题 5：每人上车数上限？

**✅ 建议决策**：**首期不限制**
- 理由：平台初期要鼓励用户多上车、多尝试
- 成本控制：通过车次名额总量控制整体折扣成本
- 二期可加：如发现薅羊毛行为，再加限制（如同模型最多 3 个进行中车次）

#### 问题 6：满员车次的已上车用户折扣

**✅ 建议决策**：**折扣享受到车次过期**（已在 §2.4 明确）
- 理由：满员只是关闭上车通道，不影响已上车用户权益
- 用户预期：上车时承诺的折扣有效期应该兑现

### ✅ 核心问题 1：`user_model_discounts` 表结构分析（已确认）

**网关表 DDL**：
```sql
CREATE TABLE `user_model_discounts` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `user_id` bigint NOT NULL COMMENT '关联用户ID',
  `models` text NOT NULL COMMENT '关联模型ID（可能是JSON数组或逗号分隔）',
  `discount_type` enum('PERCENTAGE','FIXED_AMOUNT','OVERRIDE_PRICE') DEFAULT 'PERCENTAGE',
  `discount_value` decimal(10,4) NOT NULL COMMENT '百分比填0.8表示8折',
  `start_time` datetime DEFAULT NULL COMMENT 'NULL表示立即生效',
  `end_time` datetime DEFAULT NULL COMMENT 'NULL表示永久生效',
  `status` tinyint NOT NULL DEFAULT '1' COMMENT '1启用 0禁用',
  `remark` varchar(500) DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_user_id` (`user_id`),
  KEY `idx_status` (`status`),
  KEY `idx_time_range` (`start_time`,`end_time`)
  -- 注意：没有 (user_id, model_id) 唯一约束！
);
```

**关键发现**：
| 特征 | 分析 |
|------|------|
| `models` 是 TEXT 类型 | 一行可关联多个模型（JSON数组或逗号分隔），不是单个 model_id |
| 无唯一约束 | 同一用户可以有多行折扣配置，**确认是多行模式** |
| 无 ride_id 字段 | 网关设计时未考虑拼车场景，需要用 `remark` 字段记录来源 |
| 有 start_time/end_time | 可以控制折扣有效期，**车次过期时可以直接用 end_time 控制** |
| 有 status 字段 | 可以禁用折扣而不删除，便于追溯 |

**结论：采用"多行 + 时间控制"模式**

```
拼车写入策略：
├── 上车时：INSERT 一行（models 放单个模型ID，end_time = 车次过期时间）
├── 过期时：无需操作！网关查询时自动过滤 end_time < NOW() 的行
├── 手动撤销：UPDATE status = 0（禁用）
└── 网关查询：WHERE user_id=? AND status=1 AND (end_time IS NULL OR end_time > NOW())
             然后对 models 匹配的行取 discount_value 的 min
```

**写入示例**：
```sql
-- 用户 123 上车"DeepSeek全家桶"（含2个分组）
-- 分组1：deepseek-chat 6折，分组2：deepseek-v4 8折
-- 车次过期时间：2026-09-01

INSERT INTO user_model_discounts 
  (user_id, models, discount_type, discount_value, end_time, remark)
VALUES
  (123, 'deepseek-chat', 'PERCENTAGE', 0.6, '2026-09-01 00:00:00', 'ride:1001'),
  (123, 'deepseek-v4', 'PERCENTAGE', 0.8, '2026-09-01 00:00:00', 'ride:1001');
```

**优势**：
- ✅ 不需要加分布式锁（没有并发重算问题）
- ✅ 不需要过期撤销的 node-cron 任务（网关自动过滤）
- ✅ 撤销逻辑简化为 `UPDATE status=0 WHERE remark='ride:xxx'`
- ✅ 网关零改动

**✅ 已确认**（v0.8.2）：
- [x] 网关查询时**会过滤** `end_time < NOW()` 的行 → **不需要过期撤销任务！**
- [x] `models` 字段是 **JSON 数组**格式：`["aliyun/deepseek-v4-flash","aliyun/qwen3.6-flash"]`
- [x] 模型 ID **带渠道前缀**，如 `aliyun/deepseek-v4-flash`

### ✅ 核心问题 1.1：`proxy_tokens` 表结构分析（已确认）

**网关表 DDL**：
```sql
CREATE TABLE `proxy_tokens` (
  `id` int NOT NULL AUTO_INCREMENT,
  `user_id` int unsigned NOT NULL DEFAULT '1',
  `name` varchar(255) NOT NULL,
  `key` varchar(191) NOT NULL,              -- ⚠️ 明文存储，不是哈希！
  `token_group_code` varchar(40) DEFAULT 'default',
  `models` text,                            -- 可限制该 Key 只能访问特定模型
  `quota` bigint DEFAULT '0',               -- Key 级别配额（0=不限制，用用户余额）
  `used_quota` bigint DEFAULT '0',
  `remain_quota` bigint DEFAULT '0',
  `expired_at` datetime DEFAULT NULL,       -- Key 过期时间
  `status` tinyint DEFAULT '1',             -- 1启用 0禁用
  `price_markup` decimal(10,4) DEFAULT '1.0000',  -- 价格加成
  `gift_quota` int DEFAULT '0',             -- 赠送额度
  PRIMARY KEY (`id`),
  UNIQUE KEY `key` (`key`),                 -- Key 唯一约束
  KEY `idx_token_user_id` (`user_id`)
);
```

**关键发现**：
| 特征 | 分析 |
|------|------|
| `key` 是**明文存储** | 不需要哈希算法，直接生成随机字符串 INSERT 即可 |
| 有唯一约束 `UNIQUE KEY (key)` | 生成时需检查唯一性（UUID/随机字符串通常不会冲突） |
| 有 `quota` 字段 | Key 级别配额，设为 0 表示使用用户余额 |
| 有 `expired_at` 字段 | 可设置 Key 过期时间，NULL 表示永不过期 |
| 有 `models` 字段 | 可限制该 Key 只能访问特定模型（JSON 数组） |

**拼车程序生成 Key 的逻辑**：
```typescript
import { randomBytes } from 'crypto';

async function createApiKey(userId: number, name: string = '默认密钥') {
  // 1. 生成随机 Key（sk- 前缀 + 32位随机字符）
  const key = 'sk-' + randomBytes(24).toString('base64url'); // 约32字符
  
  // 2. 直接 INSERT（明文存储）
  await gatewayDb.execute(`
    INSERT INTO proxy_tokens (user_id, name, \`key\`, quota, status)
    VALUES (?, ?, ?, 0, 1)
  `, [userId, name, key]);
  
  // 3. 返回明文 Key 给用户（仅此一次展示）
  return key;
}
```

**注意事项**：
- Key 生成后**只展示一次**，用户需自行保存
- 拼车程序不存储 Key 明文，只存储 `proxy_tokens.id` 的映射
- `quota=0` 表示不限制 Key 配额，使用用户账户余额
- `models=NULL` 表示该 Key 可访问所有模型

### 🟡 核心问题 2：`proxy_logs` 索引分析（部分确认）

**网关表 DDL**：
```sql
CREATE TABLE `proxy_logs` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `user_id` int unsigned NOT NULL DEFAULT '0',
  `token_id` int DEFAULT NULL,
  `channel_id` int DEFAULT NULL,
  `model` varchar(100) DEFAULT NULL,
  `prompt_tokens` int DEFAULT '0',       -- 注意：不是 input_tokens
  `completion_tokens` int DEFAULT '0',   -- 注意：不是 output_tokens

  KEY `idx_package_id` (`package_id`)
);
```

**拼车查询场景 vs 现有索引分析**：

| 查询场景 | 查询条件 | 理想索引 | 现有索引 | 评估 |
|---------|---------|---------|---------|------|
| 消费日志列表 | `user_id=? AND created_at BETWEEN` | `(user_id, created_at)` | `(created_at, user_id)` | 🟡 可用但非最优，需回表 |
| 消费日志+模型筛选 | `user_id=? AND model=? AND created_at BETWEEN` | `(user_id, model, created_at)` | 无 | 🔴 慢查询风险 |
| 活跃度回收 | `user_id=? AND model IN(...) AND created_at > ?` | `(user_id, model, created_at)` | 无 | 🔴 慢查询风险 |
| 累计消费统计 | `user_id=? AND model IN(...) GROUP BY` | `(user_id, model)` | 无 | 🔴 全表扫描风险 |

**结论**：
- 现有索引 `(created_at, user_id)` 对拼车查询**有一定帮助但非最优**
- 缺少 `(user_id, created_at)` 和 `(user_id, model, created_at)` 索引
- 数据量 12680 条目前不大，但会快速增长

**建议方案**：

| 方案 | 说明 | 风险 |
|------|------|------|
| A. 请求加索引 | 请网关团队添加 `(user_id, created_at)` 索引 | 需要网关配合，影响写入性能 |
| B. 同步副本 | 拼车程序建立 `pt_consumption_logs` 副本表，定时同步 | 数据延迟，维护成本 |
| C. 限制查询 | 消费日志只查最近 30 天，强制分页 ≤20 条 | 用户体验受限 |
| D. 暂不优化 | 先上线观察，慢查询超阈值再处理 | 可能影响网关性能 |

**推荐**：先采用 **方案 C + D**，上线后监控慢查询，必要时再请求加索引

**⚠️ 字段映射修正**（需求文档 §7.1 使用了错误字段名）：
| 需求文档字段 | 实际表字段 |
|-------------|-----------|
| `input_tokens` | `prompt_tokens` |
| `output_tokens` | `completion_tokens` |
| `original_amount` | 无（需计算或从其他表获取） |
| `discount_rate` | 无（存在 user_model_discounts） |
| `final_amount` | `quota_consumed` |

### 🟡 核心问题 3：`pt_ride_members.total_consumption` 维护方案（建议采用方案 B）

**背景**：活跃度回收机制需要判断"累计消费 ≥ 1 万额度则豁免"

**方案对比**：
| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| A. 异步累加 | 网关消费完成后发 MQ，拼车程序消费并累加 | 性能好，不依赖 proxy_logs 索引 | 需要网关配合发消息，或定时增量聚合 |
| **B. 定时聚合** | 每小时从 proxy_logs 增量聚合更新 | 不需要网关改动 | 依赖 proxy_logs 索引，有延迟 |
| C. 实时查询 | 活跃度回收时实时查 proxy_logs | 数据最准确 | 性能风险最大，可能拖垮网关库 |

**推荐方案 B：定时增量聚合**

```sql
-- 每小时执行：更新最近2小时有消费的用户的累计消费
-- 利用现有索引 (created_at, user_id)

UPDATE pt_ride_members rm
JOIN (
  SELECT 
    pl.user_id,
    rgm.ride_id,
    SUM(pl.quota_consumed) as consumption
  FROM proxy_logs pl
  JOIN pt_ride_group_models rgm ON pl.model = rgm.model_id
  JOIN pt_ride_groups rg ON rgm.group_id = rg.id
  WHERE pl.created_at > DATE_SUB(NOW(), INTERVAL 2 HOUR)
  GROUP BY pl.user_id, rgm.ride_id
) agg ON rm.user_id = agg.user_id AND rm.ride_id = agg.ride_id
SET 
  rm.total_consumption = rm.total_consumption + agg.consumption,
  rm.last_consumption_at = NOW();
```

**优化点**：
- 只聚合最近 2 小时的增量，避免全表扫描
- 利用现有索引 `(created_at, user_id)`
- 每小时执行，延迟可接受（活跃度回收是每日检查）
- 可以记录 `last_sync_at` 避免重复统计

## 10.3 架构风险补充（v0.8.1 新增）

### 风险 5：跨库操作没有分布式事务保障

**场景**：上车时需要：
1. 写拼车库 `pt_ride_members`（上车记录）
2. 写网关库 `user_model_discounts`（折扣）

这两步跨库，没有分布式事务，中间失败会导致数据不一致。

**状态机设计**（与充值到账类似）：

```
上车请求
    ↓
1. 写 pt_ride_members（status=PENDING）+ 写 pt_discount_tasks 任务表
    ↓
2. 异步 Worker 处理任务：
   - 遍历车次所有模型
   - 逐一写 user_model_discounts
   - 全部成功 → 更新 pt_ride_members.status = ACTIVE
   - 部分失败 → 重试，超过阈值告警
    ↓
3. 前端轮询/WebSocket 获取折扣生效状态
```

**任务表**：
```sql
CREATE TABLE pt_discount_tasks (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  ride_member_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  model_id VARCHAR(100) NOT NULL,
  discount_rate DECIMAL(3,2) NOT NULL,
  status ENUM('PENDING', 'SUCCESS', 'FAILED') DEFAULT 'PENDING',
  retry_count INT DEFAULT 0,
  last_error TEXT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_status (status)
);
```

### 风险 6：直连生产库的协作机制缺失

**问题**：文档说"Prisma schema 分离，网关表变更不会直接炸掉"——这个理由站不住脚：
- 如果网关表加了 `NOT NULL` 字段或改了约束，拼车程序的 INSERT/UPDATE 照样会失败
- Prisma schema 分离只能防止编译错误，不能防止运行时错误

**需要建立的协作机制**：

| 机制 | 说明 |
|------|------|
| 变更通知 | 网关团队变更 `user_users` / `proxy_tokens` / `user_model_discounts` / `proxy_logs` 这几张表时，必须提前通知拼车团队 |
| 联调验证 | 网关表结构变更上线前，拼车团队需要在测试环境验证兼容性 |
| 版本锁定 | 明确拼车程序依赖的网关表结构版本，记录在文档中 |
| 监控告警 | 拼车程序对网关库操作加监控，异常率上升时自动告警 |
